# Server-managed authentication: Stages 1–4

Stage 1 is an isolated design proof. Stage 2 adds a private database store, and Stage 3 adds the server identity boundary. Stage 4 wires that boundary behind an explicit application mode that defaults to the existing browser authentication. The generic morning-summary pilot and notification behavior remain unchanged. Supabase remains the identity provider.

## Session and response ordering

The server will own identity-provider access and refresh tokens. A browser receives only an opaque, random Plannix session secret in a `Secure; HttpOnly; SameSite=Lax; Path=/` **host-only** `__Host-` cookie. No `Domain` attribute is permitted. Tokens and session secrets must never be included in JSON, logs, analytics, URLs, or JavaScript-readable storage. The session secret necessarily appears in the protected `Set-Cookie` response header; JavaScript cannot read that header or an HttpOnly cookie. Logs must also omit `Cookie` and `Set-Cookie` headers.

The proposed production boundary first issues an unpredictable 256-bit browser marker as a host-only `__Host-plannix-b-<sequence>` cookie. The server stores only its hash. A login without a confirmed marker does not begin; the browser must bootstrap and retry. A missing marker is unauthenticated; an unknown, altered or duplicate marker fails closed **without automatic cookie deletion**. A server-verified expired or permanently revoked marker may receive exact-name cleanup. A caller-supplied family ID is never accepted as an identity. The marker is a bearer grouping input, **not** authentication or an owner ID; stealing its value is outside the fixation resistance proved by these tests. Host-only, HttpOnly cookie scope prevents a sibling domain or page JavaScript from setting or reading it. Production must also prevent header spoofing at its trusted ingress.

Concurrent first bootstrap responses receive *distinct marker cookie names*. Their server-issued sequence, not response order or a client value, selects the newer valid marker when both arrive. The older marker and its sessions are permanently revoked in server state **before** exact-name marker cleanup is emitted. A delayed cleanup response therefore cannot remove or make authoritative a later marker/session version. If a marker appears after an account session was created under a different marker, the session may require reauthentication; it must never select the older account. Two first login attempts on the same confirmed marker have a defined outcome: the latest **started** attempt is eligible to commit. A multi-replica implementation needs a durable atomic sequence or an equally collision-resistant server-issued name, plus atomic selection and commit. The Stage 1 in-memory sequence is only a contract model.

Each successful transition uses a *different cookie name*, for example `__Host-plannix-s-42`. Selection uses the server-side current generation, never cookie header order or the last arriving response. A stale response may add an older cookie after a newer one; the next valid selection clears it. Logout revokes the exact selected generation and clears only that version's cookie name. A delayed A logout cannot revoke or clear B. Refresh holds the same owner and generation, cannot revive a revoked record, and does not extend the fixed absolute browser-cookie lifetime. A future refresh-token rotation must atomically update only the still-current server session.

A transition is pending for at most two minutes. It can explicitly **fail**, **cancel**, or **expire**; completion after the deadline expires. Repeated completion or settlement cannot emit another cookie. A newer attempt supersedes an older pending attempt immediately. If the newer attempt then fails, is cancelled, expires or never completes, the older one stays superseded. The prior *already valid* session remains usable until a replacement commits, except for explicit logout or a security revocation. Secret generation and validation occur before revoking that prior session. Identity-provider failure, invalid identity results and secret-source failure therefore cannot silently sign out the existing account. Expired pending attempts are settled when encountered; a production transaction store needs deadline-driven cleanup as well. **Observed expiry is terminal:** shared handlers mark verified markers and sessions revoked and pending transitions expired before cleanup or rejection. Selection, begin, finish, refresh, failure and cancellation use those handlers; finish checks again immediately before committing a replacement. A backward wall-clock adjustment cannot revive an observed expired version.

Recovery uses a distinct `__Host-plannix-r-<generation>` cookie and server-side kind. Ordinary application authorization accepts only an ordinary session. Confirmation, recovery, and password-reset endpoints require their respective narrowly scoped state; completing recovery must explicitly create a new ordinary session. Never infer ordinary authorization from a Supabase recovery callback or a present recovery cookie.

The model accepts at most four marker cookies, eight session/recovery cookies, and a 4 KiB `Cookie` header. Duplicate names, malformed values, unknown names, wrong-family records and excess candidates authorize nobody. **Malformed, forged, duplicate, over-limit and oversized requests emit no automatic cleanup:** recognition of a name or prefix does not prove that deleting it is safe. The complete recognized cookie collection is checked for malformed or forged values before any expiry state change or cleanup decision. In particular, the authoritative marker and session remain intact. A request may clear a session only after matching its secret hash to a retained server record and proving that version permanently revoked or expired. A revoked/expired marker is cleared only after its own value is verified and its revocation is recorded. All cleanup is exact-name; it never targets unrelated cookies or a newer version. If the parser cannot establish that proof within its bounds, recovery requires the user to clear Plannix site cookies in browser settings and then bootstrap and reauthenticate; a future authenticated recovery flow would need separate proof. A huge unrelated cookie can likewise remain rejected until the browser removes it. Server state is capped at 1,024 marker families and eight recent session records per family; expired families are reclaimed on bootstrap. Superseded intents are weakly held except for the latest pending one per family. Browser cookies have a fixed 30-day maximum age. Arbitrarily many delayed HTTP responses can still temporarily create more cookies than the accepted limit; selection fails closed rather than choosing one. Production needs limits on in-flight transitions, durable state retention, and a monitored cleanup job.

Every state-changing cookie-authenticated request needs an exact trusted `Origin` check and a server-bound CSRF token in a custom header; SameSite alone is insufficient. Reject missing/invalid origins and tokens. Keep CORS credential origins explicit and narrow. Session cookies must not be scoped to the analytics hostname. Expiry and revocation are authoritative on the server; a remaining browser cookie cannot restore a revoked session. External Supabase revocation is detected on subsequent server verification/refresh, not atomically at the remote revocation instant.

## Migration and rollback contract

Later stages must inventory and move browser Supabase calls to authenticated server APIs before retiring browser-held tokens: login, signup, email confirmation/recovery callbacks, refresh, sign-out, account deletion, direct profile/membership/RPC/table reads and writes, and existing bearer-based Express calls. A compatibility period may accept the committed browser flow, but it must not give a legacy bearer token access to the new server-managed detail authorization path. Keep the two boundaries explicit and test them independently. Confirmation and recovery links must retain their redirect semantics while exchanging identity-provider credentials only through the intended server boundary. No production transition is part of Stage 1.

Existing users can remain on the current browser session until an explicit migration point. A secure cutover may require reauthentication; do not silently copy a Supabase refresh token out of browser storage. Rollback must disable the new boundary, revoke its sessions and detail bindings, restore the prior supported sign-in flow, and leave the generic push pilot usable. Any persistent session or binding schema is a future additive migration with restricted grants and a deployment/rollback order. The first production stage should not switch existing sessions without tested recovery and rollback.

## Notification display remains a separate gate

Server-managed sessions remove several application-level account-transition races, but they do **not** make authorization and operating-system notification display atomic. A service worker must use a narrow, revocable account/device binding, coordinate with every supported local account transition through the final authorization and display call, and fall back to generic text on uncertainty, unavailable coordination, storage failure, or network failure. A remote revocation can still race with display; an already displayed or watch-mirrored notification cannot be recalled.

Do not cut over authentication on the strength of this cookie model alone. The acceptance gate is a production-path proof with the installed Supabase SDK, real browser cookies/tabs and worker: delayed login/logout/refresh, automatic URL callbacks, account switches, recovery, storage failure, CSRF, response reordering, session expiry, and notification detail fetch/display. It must show that ordinary authentication stays usable when detail coordination fails and that no new account receives a prior account's detail. Free-text lesson and event titles may contain sensitive content; detailed text and event titles each need separate, default-off consent before any detail delivery.

## Stage 2 private-store contract and setup

`20261009120000_add_private_server_sessions.sql` is additive and must be applied **after** all earlier migrations, before a future server release that uses it. Do not activate server-managed login merely by applying it. Private bindings, transitions and sessions have RLS enabled and no browser or direct service-role table grants. The only callable storage boundary is the narrowly granted service-role `public.plannix_auth_*` RPC set. Its `SECURITY DEFINER` functions use an empty search path and qualified objects. A future request handler must derive `confirmed_owner` from a confirmed Supabase identity; service-role authority must never be exposed to a browser or delegated to a request-supplied user ID.

The database allocates cookie generations from one sequence, serializes each binding's transition/settlement/logout/refresh on its row lock, and stores only SHA-256 hashes of 256-bit server-generated marker and session secrets. At most one transition per binding remains pending; newer starts permanently supersede older ones. A signed-in replacement may begin with one session cookie only after the RPC verifies that its name, secret, kind and binding identify the current session. Forged or cross-binding cookies fail without cleanup. Failed, cancelled, expired and repeated settlements cannot revoke the current valid session. Settlement rechecks binding and transition expiry after the provisional session insert and before replacing the current session; an expired provisional row is removed. Transition expiry preserves the prior valid session, while observed binding expiry terminally revokes it. A completed transition commits the new session and revokes its predecessor in one transaction. The store retains at most eight session records and sixteen transition records per binding; pruned old versions become unknown and are rejected without cleanup. Issuance is serialized for the 1,024-binding cap. Observed expiry is recorded as terminal before an expiry response; a later clock rollback cannot revive it. The 30-day session/marker expiry and two-minute transition expiry are absolute, and refresh advances only the encrypted token version without extending the session expiry or changing its owner. A logout of a captured old cookie cannot revoke a newer version.

`server/auth/sessionTokenCrypto.js` uses Node's AES-256-GCM with a fresh 96-bit nonce per token, a 128-bit authentication tag, and associated data containing the session UUID, token purpose (`access` or `refresh`) and token version. Stage 3 also encrypts a one-use `pkce` verifier bound to its callback-state UUID. The repository sends only ciphertext envelopes and SHA-256 secret hashes to storage. Configure future **server-only** variables `PLANNIX_SESSION_TOKEN_KEYS_JSON` (JSON map of key IDs to canonical base64url-encoded 32-byte keys, at most eight) and `PLANNIX_SESSION_TOKEN_ACTIVE_KEY_ID` (one key ID in that map). No Stage 2 import reads those variables. For rotation, deploy the new key alongside old read keys, make it active, rewrite tokens through a version-checked refresh, and retain old keys until every envelope using them has expired or been re-encrypted. Missing keys and authentication failures deny token access with generic errors; never log keys, tokens, cookie values or ciphertext. Key distribution, storage, backup and operational rotation are future deployment work.

The Stage 2 repository's low-level methods accept one marker and at most one session cookie. Stage 3 adds a separate `resolve` operation that checks the complete cookie collection (at most four markers, eight sessions and 4 KiB), verifies every recognized value in the database, selects the newest verified marker and its current session, and returns exact-name cleanup only for proven non-authoritative versions. Malformed, duplicate, forged and excessive collections fail without cleanup. The router passes only this verified single-cookie selection to the Stage 2 methods. Pruned unknown versions still require manual cookie recovery. Low-level RPCs accept verified cookie hashes or an intent UUID from a trusted server caller, never a request-supplied user ID as authorization.

## Stage 3 isolated HTTP boundary

`20261010120000_add_server_auth_boundary.sql` follows Stage 2 and is additive. It adds private one-use PKCE callback state and a compare-and-swap refresh claim. Applying it alone does not activate any route. Stage 4 adds an explicit disabled-by-default application mode. The default bearer mode neither instantiates nor mounts the server-session runtime, and the generic notification pilot remains unchanged.

The isolated boundary uses `/__stage3/auth` with `GET /bootstrap`, `GET /status`, `POST /login`, `POST /signup`, `POST /recover`, `GET /callback`, `POST /recovery/password`, `POST /refresh`, `POST /logout`, and `DELETE /account`. Stage 4 mounts it in the explicit server mode, while the default bearer mode leaves it inactive. Requests require one exact configured `Host`, ignore forwarded-host values, reject encoded auth paths, and require the exact trusted `Origin` on mutations. The router and ordinary application-session guard share the same Origin and session-bound CSRF policy. Read-only GET/HEAD/OPTIONS may omit Origin; a supplied Origin must still match. Responses are non-cacheable; JSON bodies are limited to 8 KiB. Unsupported, malformed and oversized parser inputs receive bounded generic JSON from router-local error handling, without relying on Express's default error response. The CSRF token is an HMAC tied to the selected marker and session cookie and is supplied only in a custom header. A bootstrap marker is server-generated before login, signup or recovery. `__Host-` cookies are `Secure`, `HttpOnly`, host-only, `SameSite=Lax`, and fixed-lifetime. Local tests use HTTPS browser cookie handling. An additive service-role PostgreSQL limiter now replaces the earlier per-process counter in the server-mode router; its migration and ingress configuration remain separate deployment gates.

Identity operations use the installed Supabase SDK with request-local in-memory PKCE storage and bounded, redirect-rejecting transport. Password login and session-bearing signup issue an ordinary cookie only after `getUser` confirms identity and email confirmation, and the personal-organisation/profile steps succeed. Confirmation and recovery links return to the exact configured callback URL with a server-generated state and SDK PKCE flow ID. Each callback reservation records its initiating transition, generation and current session under the browser-binding lock. Signup and recovery both begin a transition before contacting the provider. The SDK verifier attaches only to that reservation. Reservation, verifier attachment and readiness recheck eligibility after their database writes, so a delayed write cannot leave a revivable link after observed expiry. A successful email initiation leaves its transition pending and extends its deadline to the one-use link's fifteen-minute window when marking the callback ready; this permits a legitimate confirmation or recovery link without letting a superseded initiation revive. Failure, cancellation, expiry, a changed current session or a newer transition makes the callback unclaimable. Claim atomically verifies the initiating transition and starts the exchange transition under the same binding lock; it cannot create a fresh transition after supersession. After potentially delayed database work, claim rechecks the callback, initiating transition, binding and original session against fresh database time before returning a verifier. A failed recheck terminally invalidates the provisional exchange, so it cannot later settle or replace the current valid session. The callback must still be valid when claim completes. Once validly claimed, provider exchange may complete after the original callback deadline, but only within its separate two-minute exchange-transition deadline and the router's shorter provider-call deadline; settlement rechecks that exchange deadline. A newer login during provider exchange supersedes the exchange transition, and final settlement must return `created` before the router issues a session cookie. The callback chooses `/settings`, `/reset-password`, or `/profile` for an identified email change. If email issuance succeeded but the HTTP outcome is uncertain, the resulting link may be unusable and the user must request another link. A failed cancellation RPC leaves state pending and unclaimable. Recovery sessions have a different cookie kind and cannot pass the ordinary guard. Password update consumes the recovery session and requires a new ordinary login. A server-side refresh claim is acquired and released outside the provider request; database row locks are not held while Supabase is called. The final token replacement checks the claim, session/version and terminal expiry under lock. Logout revokes only the selected cookie version. Future “Sign out anyway” must revoke the captured server session and any future detail authorization independently of push-subscription cleanup, while preserving the Stage 1 version-specific ordering.

For a future activation, configure exact server-only application origin, a separate 32-byte or stronger CSRF HMAC key, Supabase URL, publishable key and server-only secret/service-role key, and the Stage 2 token keyring. Keep all provider and token keys out of browser bundles and logs. Stage 4 introduces explicit configuration and a guarded production route mount, but production cookie mode remains disabled until the new limiter migration, ingress configuration and other activation gates are reviewed. The service role must remain server-only. Real ingress must preserve the application `Host` exactly or be explicitly configured and tested for its trusted proxy behavior. Do not enable a dual-auth fallback to this session boundary.

The Stage 3 tests use synthetic provider transport and browser cookies; they do not verify real email-provider delivery, deployed reverse-proxy headers, remote account deletion side effects or production rate-limit distribution. A timed-out provider operation may still complete upstream after the HTTP deadline; a terminal transition prevents stale cookie issuance, but external provider side effects require operational reconciliation. Supabase refresh-token rotation after an ambiguous provider outcome can require reauthentication; the database will not overwrite a newer token version. Browser accounts already signed in under the old flow remain there until a separately reviewed cutover; no browser token is copied into the new store. Confirmation/recovery link templates, allowed redirect configuration and old-link compatibility must be tested before cutover. Rollback disables the new route, revokes its sessions and future detail bindings, and retains the existing generic-notification behavior. Stage 3 does not close the service-worker authorization-to-OS-display race, nor activate detailed notifications.

The full application migration chain can be tested in a uniquely named disposable local database with schema-only Supabase platform definitions; the existing development database must not be reset. Run `node --test server/auth/sessionTransitions.test.js server/auth/sessionTokenCrypto.test.js server/auth/privateSessionRepository.test.js`, the `server_managed_sessions.test.sql` pgTAP file against that disposable target, and `node scripts/test-private-session-concurrency.js <verified-disposable-database>`. The concurrency runner refuses Docker connection overrides, a non-local container, a non-empty fixture database and non-disposable database names. It observes `pg_stat_activity` lock waits before releasing the first transaction.

## Stage 4 local integration and activation gates

The application now has exactly two explicit build/runtime modes: the committed `bearer` default and an opt-in `server` mode. Set `VITE_PLANNIX_AUTH_MODE=server` for a temporary frontend build and `PLANNIX_AUTH_MODE=server` for the matching Express process. Each Vite build emits an `auth-mode.json` artifact. Express validates it against its runtime mode before serving any HTML or browser asset; missing, malformed and mismatched metadata block serving, and production startup fails. Deploy the HTML, assets and metadata together. The cookie client sends no bearer token, and the cookie server rejects Authorization headers. The server-mode Vite build replaces the browser Supabase client with a throwing stub; it contains no Supabase session-storage or refresh-token implementation. No browser refresh token is imported or copied. The browser API and Express server must share **one origin** in this mode; the cookie transport rejects a different `VITE_API_BASE_URL`. Local Vite proxying preserves the original Host for this mode. All cookie calls include same-origin credentials, and all unsafe calls use the current session-bound `X-Plannix-CSRF` token. Failed authorization is surfaced; there is no bearer fallback or automatic replay of an unsafe operation.

Server-only runtime settings are `PLANNIX_SERVER_AUTH_ORIGIN` (one exact HTTP localhost or HTTPS application origin), `PLANNIX_SERVER_AUTH_CSRF_KEY` (canonical base64url of at least 32 random bytes), the Stage 2 `PLANNIX_SESSION_TOKEN_KEYS_JSON` and `PLANNIX_SESSION_TOKEN_ACTIVE_KEY_ID`, plus the existing `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and `SUPABASE_SECRET_KEY`. These settings are required only when `PLANNIX_AUTH_MODE=server`; do not place them in `VITE_` variables. The current server-mode router remains at `/__stage3/auth` and is mounted only after the analytics-host boundary and security headers. It adds `GET /me`, `PUT /profile/name`, `POST /profile/email`, and `POST /profile/password`. The new `/api/memberships` endpoint is available only in cookie mode. All other existing authenticated APIs reuse the session guard and a request-scoped Supabase client with the **verified user's access token**, so RLS remains authoritative. The service role remains confined to the private session RPCs and previously privileged operations; it does not replace user-scoped application reads/writes. Public Contact and holiday-country endpoints remain public.

The browser adapter handles login, signup, callback restoration, recovery, refresh on restoration, Profile operations, version-specific logout, deletion, and cross-tab UI invalidation. Session reloads distinguish authenticated, confirmed signed-out, stale and verification-failed outcomes; obsolete reloads cannot announce sign-out. A confirmed account deletion with uncertain subsequent session verification offers a status-only Retry that never resends the deletion request. Cleanup and redirect apply only while the captured session is current. A status response identifying another account triggers central reconciliation even without focus or navigation. Profile unmount disposes its deletion controller, aborts a pending status read where supported, and ignores late results even when abort is ignored. Disposal does not undo an already accepted deletion. Every server-mode Profile visit verifies current server status before showing account details; confirmed sign-out updates App state, while an unknown result offers a status-only Retry. Returning after accepted deletion requires no Delete click. Initial pre-deletion session verification is bounded and disposal settles its wait even if the request ignores abort. A remounted editor never repeats deletion automatically. The ordinary application guard refreshes an expired provider access token under the database's version-checked claim. A competing or uncertain refresh fails the request safely instead of forwarding a stale token. It retains the current draft confirmation and push cleanup flow. A rejected draft sign-out does not call notification cleanup. If a cookie-mode logout cannot be confirmed, the UI retains the session and offers retry; “Sign out anyway” still requires explicit consent when push cleanup fails and then revokes the captured cookie session. An old tab sends its captured session name when signing out or deleting an account; the server rejects a request selected to a newer version. Late logout, profile and account-deletion results cannot clear a newer account's local view. The client also checks account generations after transport and JSON parsing. BroadcastChannel and focus reconciliation update other tabs; a transient focus-time verification outage leaves an existing draft intact, while a confirmed unauthorized status clears the UI. Database generations and CSRF remain the security boundary if browser events are delayed or unavailable. Already-started user-authorized mutations can still have uncertain upstream outcomes; Profile email/password timeouts abort further SDK transport, issue no new cookie, and tell the user to reconcile rather than claim failure or rollback.

In server mode, the displayed account and exact session-cookie version form the request context. Status reads that identify another session invalidate the old context and announce reconciliation; they cannot silently install its CSRF token. The old protected component tree, its in-memory drafts and pending data requests are discarded when a session change is detected. Drafts are never transferred to the newly verified account; users must re-enter unsaved work after an account change. A same-account replacement also invalidates late results from the prior session version. An uncertain reconciliation hides protected content and offers status-only Retry. The controller verifies the new account and profile first; the UI activates its CSRF/request context only after rendering that account. Every ordinary application request carries `X-Plannix-Expected-Session`; the shared server guard compares it with the verified cookie session before any route write. Profile changes, password changes and account deletion use the same version precondition in the auth router. This header is only a stale-UI precondition, never a source of ownership: the server still derives owner and RLS token from the selected private session. A mismatch returns 409 without replaying the mutation under the newly selected account. The old browser UI cannot authorize B with B's newly observed CSRF token. A response already accepted by an upstream provider remains potentially ambiguous and requires reconciliation.

**Production remains in bearer mode.** The additive `20261011120000_add_server_auth_rate_limits.sql` and `20261016120000_add_server_auth_rate_epoch.sql` migrations must be applied in order before a separately approved server-mode activation. The latter starts **paused**, revokes the old one-argument claim RPC from `service_role`, and requires `PLANNIX_AUTH_RATE_EPOCH` (a positive database-issued integer) in addition to `PLANNIX_AUTH_RATE_KEY` (one canonical base64url key of at least 32 random bytes, identical on all replicas), `PLANNIX_AUTH_TRUSTED_PROXY_CIDRS` (reviewed immediate socket-peer CIDRs) and `PLANNIX_AUTH_INGRESS_CIDRS` (separately reviewed `X-Forwarded-For` ingress-address CIDRs). The RPC also compares a private HMAC-derived key tag with the operator-prepared epoch, so an old-key process given a new epoch still cannot claim. Missing or malformed settings block production startup; paused, wrong-epoch/key-tag, missing or failing RPC results block each sensitive operation with a generic 503 before provider or transition work. No bypass flag exists. Startup does not verify remote migration state, so rollout must test the RPC and grants before switching modes. Keep the deployed frontend in `bearer` mode while this gate remains. Before activation, verify the real ingress preserves the exact public Host, serves the UI and API on the same origin with TLS, and does not route the analytics hostname to auth/application APIs. Validate the complete chain in a disposable database, review grants and provider-link templates, and apply those additive migrations only through a separately approved deployment. Recheck actual signup, recovery and email-change links, especially links issued by the old browser flow: old links are **not** silently upgraded to the new PKCE/binding state. Users with old browser sessions must reauthenticate; expired or incompatible links need reissuance. No existing browser refresh token is migrated. Controlled rollback must switch the frontend and server modes together, revoke server sessions and future detail bindings, and require affected users to sign in again under the prior flow. Never enable simultaneous fallback for the same protected route.

### Shared auth rate limiting and ingress contract

The limiter uses atomic PostgreSQL claims with database-clock, fixed one-minute windows. Separate categories cover bootstrap (60/network), status and current-user reads (180/network, 150/verified binding each), login (20/network, 12/verified binding, 8/network-plus-email), signup (10/8/5), recovery (10/8/5), callback (25/12), profile-name updates (30/20), email/password changes and recovery password update (10/6 each), refresh/logout (120/90 each), and deletion (6/4). Keys are HMACs of category and network, verified marker name, or network-plus-normalized-email. Neither raw email nor IP is stored. There is no global email counter that an outsider could trivially exhaust to lock out that account. A 429 has a bounded 1–60-second `Retry-After`; store errors or a three-second claim timeout return generic 503 before a provider call or auth transition. A timed-out database claim may still count later, conservatively reducing remaining attempts. Fixed-window boundaries permit a burst around a minute change, and shared-network limits can affect unrelated users behind one NAT.

**Rate-key rotation is a maintenance operation, not a rolling secret update.** The privileged operator runs `select private.plannix_auth_rate_pause()` using a trusted SQL connection, never a browser or the app's `service_role`. The pause update waits for all in-flight claim transactions holding the control row's shared lock, then records `paused_at` with database time. New or queued claims fail closed; `/health` remains independent. This does **not** cancel HTTP requests that passed the limiter and entered a provider or auth transition earlier. Stop admission and drain those requests separately, including work whose client-side three-second limiter wait timed out; record evidence of quiescence. While paused, derive a non-secret tag with `HMAC-SHA256(PLANNIX_AUTH_RATE_KEY, 'plannix-auth-rate-key-v1')`, then run `select private.plannix_auth_rate_prepare_epoch('<64-hex-tag>')` once to allocate a strictly higher epoch. The key stays in the secret store; only its tag is supplied to privileged SQL. Configure every replacement replica with that returned `PLANNIX_AUTH_RATE_EPOCH` and the same new HMAC key. Old replicas cannot claim under the new epoch or key tag. Only after the old requests have drained, all replacement replicas are ready, and at least **60 database-clock seconds** have elapsed since `paused_at`, run `select private.plannix_auth_rate_resume(<prepared epoch>)`. Resume refuses an early or wrong-epoch request. The fixed buckets last one database-clock minute; two-minute row retention is cleanup, not an allowance window. Monitor the generic 503 response during the pause without logging keys or identities. A paused database makes sensitive auth unavailable, including callbacks; do not perform this without a maintenance window and recovery plan.

If deployment is interrupted, leave the database paused. An already prepared epoch is never reused: prepare another if the replacement configuration changes, then complete the same drain/wait/reopen procedure. Rollback to an earlier application or HMAC key is another rotation with a **new** epoch, even if that key was used previously. Old epoch instances never regain claim access. Database pause is an admission control, not proof that already admitted provider operations ended; external HTTP draining and real ingress observations remain staging gates. DigitalOcean App Platform's ability to drain those requests through a rolling deployment is unverified. If quiescence or uniform replica configuration cannot be verified, leave auth paused and keep `/health` available; do not use an ordinary rolling key update.

DigitalOcean's current App Platform guidance identifies `do-connecting-ip` as the visitor IP and `X-Forwarded-For` as the ingress server IP: https://docs.digitalocean.com/support/where-can-i-find-the-client-ip-address-of-a-request-connecting-to-my-app/ . The limiter uses the former **only** when the socket's immediate peer belongs to `PLANNIX_AUTH_TRUSTED_PROXY_CIDRS`, and requires the latter to be one different IP in `PLANNIX_AUTH_INGRESS_CIDRS`. The lists are deliberately separate: trusting an ingress header address must not make it a trusted socket peer. Missing, duplicate, comma-appended, malformed or conflicting headers fail closed on the trusted-proxy path. `Forwarded` or `X-Real-IP` is treated as a competing identity claim and rejected; `X-Forwarded-Host` never selects identity. An untrusted direct peer supplying either expected header fails closed; a direct peer without identity headers uses its socket IP.

Both allowlists must contain at most 32 explicit CIDRs each, with network (host) bits zero and no overlap. Each IPv4 range must be /24 or narrower and each IPv6 range /64 or narrower. Across each list, total IPv4 coverage may not exceed one /24 and IPv6 coverage may not exceed one /64; this also rejects adjacent entries whose combined coverage is too broad. The validator parses dotted and hexadecimal IPv6 forms to a binary range and rejects **any** range intersecting IPv4-mapped IPv6 space, because the installed `proxy-addr` matcher can otherwise match IPv4 peers through the IPv6 allowance. Empty comma-separated entries are invalid. These are conservative configuration guards against accidental blanket trust, **not** evidence that a permitted network belongs to DigitalOcean. They intentionally exclude legitimate larger or overlapping provider allocations; if the real ingress requires those, leave server mode disabled until a separately reviewed network-identity design is available. No provider CIDR is bundled or guessed. Review the actual immediate peer, ingress header address, and whether App Platform overwrites client-supplied `do-connecting-ip` rather than merely appending it. Published guidance does **not** establish the immediate peer CIDR or the overwrite guarantee. The existing Express `TRUST_PROXY_HOPS` setting is not authority for this limiter. If the hosting behavior cannot satisfy this contract, leave server mode disabled and use a verified ingress layer first.

Counter rows expire after two minutes. Each claim removes at most 100 expired rows; during long idle periods, operations staff may call the service-role-only `plannix_auth_rate_cleanup(max_rows)` RPC in bounded batches. Do not expose it to browsers. Monitor 429/503 rates and table size without logging keys, emails, passwords or tokens. The store reuses PostgreSQL infrastructure, but consumes database capacity; it is not free. The migration must precede any server-mode rollout. A missing function, unavailable database or invalid response fails closed; this protects sensitive auth operations but can temporarily block sign-in and recovery.

#### Staging verification runbook (not an activation instruction)

Use a separate Supabase project and a separate web app with synthetic accounts. Never reuse production service credentials, session encryption/CSRF/rate keys, data or email settings. Build with `VITE_PLANNIX_AUTH_MODE=server`, leave `VITE_API_BASE_URL` unset, and run with `PLANNIX_AUTH_MODE=server` and exact matching `PLANNIX_SERVER_AUTH_ORIGIN`/`FRONTEND_ORIGIN` for the assigned HTTPS hostname. Keep `MORNING_SUMMARY_POLLING_ENABLED`, `MORNING_SUMMARY_WORKER_ENABLED`, analytics measurement variables and detailed notification delivery disabled. Use encrypted runtime-only settings for `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, `PLANNIX_SERVER_AUTH_CSRF_KEY`, `PLANNIX_SESSION_TOKEN_KEYS_JSON`, `PLANNIX_SESSION_TOKEN_ACTIVE_KEY_ID`, `PLANNIX_AUTH_RATE_KEY`, `PLANNIX_AUTH_RATE_EPOCH`, `PLANNIX_AUTH_TRUSTED_PROXY_CIDRS` and `PLANNIX_AUTH_INGRESS_CIDRS`. Generate independent 32-byte cryptographic keys and encode them canonically as base64url; do not print or log their values. Apply all migrations in order to the *new* project only. The rate-control migration starts paused: prepare an epoch with its derived key tag, configure all instances with it, wait the full database-clock interval and resume only after validating the ingress contract and shared RPC/grants.

Before admitting auth traffic, inspect the real transport `Host`, socket peer, `do-connecting-ip` and `X-Forwarded-For` with controlled synthetic requests. Record only header presence, counts, validity and comparisons against known test values, not cookies, tokens, raw visitor addresses or callback query strings. Test client-supplied duplicates and spoofed values. Obtain DigitalOcean confirmation of whether it overwrites `do-connecting-ip` and which immediate-peer/ingress networks are stable. The published client-IP article does not provide either guarantee. Do not set a broad trusted range to make tests pass. Verify the analytics hostname serves no auth/API/SPA route, including encoded paths. Keep `/health` available during a database pause, but independently drain requests already admitted before changing rate keys. Test new and old replicas, interruption and rollback while paused; a successful limiter pause alone is not evidence of provider-operation quiescence.

With dedicated staging accounts, exercise signup/confirmation, recovery, email change, refresh/expiry, logout, deletion, profile edits, account switching, CSRF, rate limits and representative RLS-backed reads/writes. Signup, recovery and email-change checks send real email to a staging inbox and need separate authorization. Old browser links are not upgraded; test their failure/reissue with synthetic staging links. Roll back by pausing, draining, deploying a matched bearer build/runtime, revoking staging server sessions and requiring reauthentication; never add a fallback on protected routes. Preserve the detailed-notification display gate: server sessions do not make authorization and OS display atomic. Staging provisioning, real ingress guarantees and production cutover remain separately approved steps.

Authenticated server-mode mutations require an immutable account, session-cookie version and generation captured before asynchronous preparation. Timetable snapshot loading and queued lesson saves carry that original context through transport; a stale queued edit cannot be dispatched under a later account or a replacement session. The browser transport rejects authenticated mutations without explicit context before status preflight or network transmission. Login/signup bootstrap, recovery and internal refresh use their separate auth-session contracts. Bearer mode retains its existing transport. The server's verified-cookie and expected-session checks remain a second safeguard; neither browser context checks nor an abort can undo a mutation already accepted upstream.
