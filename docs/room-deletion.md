# Atomic room deletion

The additive `20261123120000_delete_room_and_clear_class_defaults.sql` migration must precede the matching API deployment. The already-applied rooms foundation is unchanged. Older code continues to reject referenced rooms; it cannot accidentally clear defaults.

`plannix_delete_room(uuid, uuid)` runs with the caller's authenticated identity and RLS. Only a confirmed Organisation Admin for the target organisation can use it. PUBLIC, anon and service_role have no execution grant. The API uses the existing user-scoped client, including server-managed session validation.

The transaction locks organisation academic years in ID order, then class rows in ID order, then the target room. Year/class locks use NO KEY UPDATE to allow session-insert foreign-key KEY SHARE checks while still excluding conflicting class updates. This follows ordinary class saves (year before class before room). Existing assignment triggers SHARE-lock rooms; a concurrent assignment must either commit first and be considered, or wait and reject a deleted room. Deferred foreign keys remain unchanged. Any session reference, including dated overrides, rejects the entire deletion. A final DELETE returning no row (for example after concurrent Admin revocation) raises an error and rolls back default clearing and revision changes. No session row is modified. Default-only deletion clears defaults across all organisation years and advances each affected class revision once. Archived rooms follow the same rules.

Each database lock wait is bounded to two seconds; this is not a total request deadline. Deadlock detection, contention or any transaction error rolls back all changes. The API never retries deletion automatically. A network/commit uncertainty requires explicit reload of rooms and classes before another attempt; readback is not an idempotent replay. Stale class saves are rejected by the revision fence and room FK/assignment triggers.

The confirmation explains default clearing. Save or reload unsaved class changes first. Class editing is blocked through deletion and class refresh. Success is shown only after room absence and refreshed class state are confirmed. Account/session/organisation/year changes invalidate those completions. The existing explicit reload handles uncertain outcomes without repeating the mutation.

Local verification includes fresh migrations, pgTAP permissions/rollback checks, held concurrent assignments in both orders, database-backed HTTP routes in both authentication modes, and rendered Classes/Rooms recovery and class-refresh tests. These do not establish production gateway configuration; production application, catalog postchecks and deployment remain separate operator actions.
