# Web Push registration and test notifications

This phase supports per-device registration and a generic test notification. It does not schedule or send morning summaries. A successful test response means the browser vendor's push service accepted the request, not that the device displayed it.

## Deployment order

1. Review and apply `20261002190000_add_personal_push_subscriptions.sql` in the normal Supabase migration process. The table is private; browser roles have no table or RPC access. The confirmed-session Express API performs the service-role-only RPC calls. Do not deploy the UI before the migration.
2. Generate one VAPID key pair with `npx web-push generate-vapid-keys` in a trusted environment. Do not commit the private key or copy it into a `VITE_` variable. Keep this key pair stable: rotating it invalidates existing browser subscriptions.
3. Configure the server with `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, and `VAPID_SUBJECT`. The subject must be a real `mailto:` contact or HTTPS URL controlled by the operator. The private key is read only by the server. The authenticated `/api/notifications/config` response returns only the public key.
4. Deploy the server and same-origin `/push-sw.js` together with the client build. Production requires HTTPS. Ensure the host permits outbound HTTPS to supported browser push-service hosts: `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `web.push.apple.com`, and `*.notify.windows.com` / `*.wns.windows.com`. No proxy, redirect, custom endpoint or scheduler is configured by this feature.
5. In Settings → Notifications, a user explicitly enables notifications and may send a test. On iPhone/iPad, the web app must first be installed on the Home Screen. A user may subscribe up to ten devices; each endpoint belongs to at most one user. Normal sign-out confirms draft discard first, then waits for pending notification registrations and attempts device cleanup within an eight-second deadline. If cleanup cannot be confirmed, the session and drafts remain and Retry is shown. Once cleanup succeeds, the existing Supabase Auth logout runs with its committed behavior and no notification-specific timeout or auth gate. New notification registrations remain blocked until that logout settles. A rejected draft-discard confirmation never starts cleanup.

When Web Locks are available, all app device-subscription reads and mutations that can lead to registration or removal use one exclusive browser Web Lock, including status reconciliation and test-send expiry handling. Unknown or false server status never authorizes browser unsubscription; the user may Retry status or explicitly Enable to reassign the device. Without Web Locks, Enable, Disable and Test are unavailable. Normal sign-out instead captures the browser subscription identity and attempts only the confirmed-account, versioned server removal within the cleanup deadline; it never unsubscribes the browser without coordination. Confirmed removal or absence permits ordinary logout. If server cleanup fails or times out, the session and drafts remain with Retry and an explicit “Sign out anyway” choice explaining that notifications may remain enabled on this device. Sign out anyway reconfirms draft discard and the notification risk; it never claims cleanup succeeded. An old removal finishing after a timeout cannot delete a newer server version, but its outcome may remain uncertain to the user.

On browsers with Web Locks, a cleanup request that exceeds the UI deadline may continue inside its Web Lock until it actually settles. The sign-out registration guard blocks new registrations through a successful SDK logout; after a cleanup failure it releases so the still-signed-in user can retry. The lockless fallback does not provide cross-tab coordination for browser subscription state, which is why it performs no browser unsubscribe.

External authentication revocation cannot preserve a session that has already ended. It does not perform destructive notification cleanup from an unscoped signed-out callback; the prior browser subscription may remain until the user explicitly reconciles it. Supabase Auth's pre-existing cross-tab logout, automatic callback and refresh behavior is unchanged, including its existing race limits. Notification cleanup can add up to eight seconds before the SDK logout starts, increasing the time in which another tab might change auth state; it does not extend or overlap an in-flight SDK logout beyond the committed auth behavior. A concurrent auth change in another tab is still outside this feature's guarantee. Account-scoped checks and the device Web Lock protect notification ownership only; they are not a cross-tab auth lock.

The worker contains only `push` and `notificationclick` handlers. It never caches or intercepts requests. It accepts only a fixed, versioned test payload, displays generic text, and opens the same-origin Notifications settings page. Push endpoints and encryption keys are stored in the private subscription table, never in browser storage. Test sends are limited to one per user per minute across all devices in the database. Ordinary device removal first claims the current endpoint and encryption keys, then atomically removes only that owner's claimed version. Already-absent and superseded versions are not reported as removal of a newer registration. Expired 404/410 subscriptions likewise remove only the exact claimed version; a replacement remains registered. Other provider errors are replaced with safe messages; no endpoint, keys or provider response is logged or returned.

There is no scheduler or morning-summary preference in this phase. A future scheduler would require its own authenticated recipient-selection and payload design. Push delivery itself is best-effort and cannot be confirmed end-to-end by this API.
